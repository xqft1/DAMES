# DAMES

> **Mint with ETH. Stake liquidity. Earn the ETH.**

**DAMES** is a fixed-supply ERC-20 protocol deployed on **Robinhood Chain**.

DAMES has a maximum supply of **21,000,000 tokens** and no conventional token sale or fixed mint price. New DAMES are issued exclusively through an exponential bonding curve implemented by `DamesBreeches`.

ETH contributed to mint DAMES is not retained by the minting contract or sent to a protocol treasury. **100% of mint ETH is forwarded atomically to `DamesBounty`**, where it is distributed over time to users staking DAMES/ETH Uniswap v2 LP tokens.

## Protocol overview

The DAMES protocol consists of three core contracts:

```text
                    ETH
                     │
                     ▼
              DamesBreeches
                     │
          ┌──────────┴──────────┐
          │                     │
          ▼                     ▼
      Mint DAMES           100% of ETH
          │                     │
          ▼                     ▼
        User              DamesBounty
                                │
                                ▼
                       DAMES/ETH LP stakers
                                │
                                ▼
                          ETH rewards
```

The protocol deliberately has a narrow scope.

There are:

- no NFTs
- no transfer taxes
- no token reflections
- no staking emissions
- no governance token
- no minting treasury allocation
- no adjustable bonding curve
- no protocol fee deducted from mint ETH

DAMES issuance, liquidity and ETH rewards form the entire core system.

# DAMES monetary policy

## Maximum supply

Let:

```text
M = 21,000,000 DAMES
```

The maximum token supply is enforced both economically by the bonding curve and technically by the ERC-20 supply cap.

The bonding curve approaches this maximum as more ETH is contributed.

---

# The bonding curve

DAMES uses an exponential issuance curve.

Let:

- `M` = maximum DAMES supply
- `E` = cumulative ETH contributed
- `K` = curve scale
- `S(E)` = total DAMES supply implied by the curve

For DAMES:

```text
M = 21,000,000
K = 100 ETH
```

The curve is:

$$
S(E) = M(1-e^{-E/K})
$$

Therefore:

$$
S(E) = 21,000,000(1-e^{-E/100})
$$

This means DAMES issuance is highest at the beginning of the curve and progressively decreases as cumulative ETH contributions increase.

The curve does **not** change.

`K` is stored as an immutable value inside DamesBreeches.

---

# Calculating a mint

A user does not simply receive DAMES according to a fixed `DAMES per ETH` rate.

Instead, the contract calculates the total supply that should exist before and after the ETH contribution.

If cumulative ETH before a transaction is:

$$
E
$$

and a user contributes:

$$
\Delta E
$$

then the DAMES minted are:

$$
\Delta S = S(E+\Delta E)-S(E)
$$

or:

$$
\Delta S =
M(1-e^{-(E+\Delta E)/K})
-
M(1-e^{-E/K})
$$

which simplifies to:

$$
\Delta S =
M(e^{-E/K}-e^{-(E+\Delta E)/K})
$$

This guarantees that every mint moves the protocol further along the same deterministic issuance curve.

# Marginal issuance

Differentiating the supply curve gives the instantaneous issuance rate:

$$
\frac{dS}{dE}
=
\frac{M}{K}e^{-E/K}
$$

For DAMES:

$$
\frac{M}{K}
=
\frac{21,000,000}{100}
=
210,000
$$

At the very beginning of the curve, the theoretical marginal issuance rate is therefore:

```text
210,000 DAMES per ETH
```

As cumulative ETH increases, this rate falls exponentially.

Approximate marginal issuance:

| Cumulative ETH | Marginal DAMES / ETH |
|---:|---:|
| 0 | 210,000 |
| 100 | 77,255 |
| 200 | 28,420 |
| 300 | 10,455 |
| 400 | 3,846 |

These figures describe **bonding-curve issuance**, not the secondary-market price of DAMES on Uniswap.

---

# Why supply approaches 21 million

The exponential term:

$$
e^{-E/K}
$$

approaches zero as cumulative ETH increases.

Therefore:

$$
\lim_{E\to\infty}
M(1-e^{-E/K})
=
M
$$

and consequently:

$$
\lim_{E\to\infty}S(E)
=
21,000,000
$$

At sufficiently large exponents, the fixed-point exponential implementation numerically resolves the decay term to zero, at which point the contract returns the exact `MAX_SUPPLY`.

The ERC-20 cap independently prevents supply from ever exceeding 21,000,000 DAMES.

---

# No redemption curve

DamesBreeches is an **issuance curve**, not a two-way bonding market.

Users can:

```text
ETH → DAMES
```

through DamesBreeches.

There is no corresponding:

```text
DAMES → ETH
```

redemption function in DamesBreeches.

Secondary trading takes place through external liquidity markets such as the DAMES/ETH Uniswap pool.

This separates:

- protocol issuance
- secondary-market price discovery
- liquidity provision

---

# Mint slippage protection

DamesBreeches exposes:

```solidity
mint(uint256 minDamesOut)
```

The frontend obtains a quote before submitting a mint.

Because other DAMES mint transactions can execute first and move the curve, the user specifies the minimum acceptable DAMES output.

If:

```text
actual DAMES < minDamesOut
```

the transaction reverts.

This prevents a user from unexpectedly receiving materially fewer DAMES due to transaction ordering.

---

# Where mint ETH goes

DamesBreeches does not retain ETH.

Every successful mint executes an atomic call equivalent to:

```solidity
DamesBounty.fundRewards{value: msg.value}();
```

Therefore:

```text
ETH contributed to mint
        =
ETH delivered to DamesBounty
```

There is no separate accounting parameter specifying how much ETH was deposited.

`msg.value` itself is the reward amount.

This is an important security property: reward accounting cannot report a mint reward unless the corresponding ETH is physically delivered to DamesBounty in the same transaction.

If the reward transfer fails, the entire mint reverts.

---

# DamesBounty

DamesBounty converts protocol mint activity into native ETH yield for DAMES/ETH liquidity providers.

Users:

1. provide DAMES + ETH liquidity
2. receive Uniswap v2 LP tokens
3. stake those LP tokens in DamesBounty
4. earn ETH contributed by future DAMES minters

No DAMES tokens are created as staking rewards.

The staking reward is **native ETH**.

---

# Seven-day reward streaming

Mint ETH is not distributed instantaneously.

Instead, rewards are streamed over:

```text
604,800 seconds
```

or:

```text
7 days
```

For reward amount `R`, the approximate stream rate is:

$$
r = \frac{R}{604800}
$$

where `r` is the amount of ETH released per second.

This reduces the effectiveness of temporarily staking liquidity immediately around a known mint solely to capture the entire reward.

---

# Rolling reward streams

If another DAMES mint occurs while a reward stream is already active, DamesBounty calculates the undistributed portion of the existing stream:

$$
R_{remaining}
=
(T_{finish}-T_{now})r
$$

The next stream then consists of:

$$
R_{new}
=
R_{mint}
+
R_{remaining}
+
R_{queued}
$$

and a fresh seven-day distribution rate is calculated.

Consequently, repeated DAMES minting continuously rolls ETH into the reward stream.

---

# Reward-per-token accounting

Let:

- `r` = ETH reward rate per second
- `Δt` = elapsed time
- `L` = total LP tokens staked
- `A` = accumulated ETH reward per LP token

During an interval:

$$
\Delta A
=
\frac{\Delta t \cdot r}{L}
$$

The implementation uses `1e18` fixed-point precision.

A user's newly accrued reward is approximately:

$$
R_u
=
L_u(A-A_{paid})
$$

where:

- `L_u` is the user's staked LP balance
- `A_paid` is the reward-per-token value previously accounted for that user

This means reward ownership is proportional to LP stake **and time staked**.

---

# New stakers

A user entering DamesBounty does not receive rewards that another staker has already accrued.

Suppose Alice is the only LP staker and a reward stream begins.

Until Bob stakes:

```text
Alice receives 100% of streamed rewards
```

Once Bob stakes, the **remaining future stream** is divided proportionally between Alice and Bob according to their LP balances.

Rewards Alice accrued before Bob entered remain Alice's.

---

# Zero-staker protection

If DAMES are minted while no LP tokens are staked, the ETH is not lost and the reward clock does not run.

Instead:

```text
mint ETH → queuedRewards
```

When LP staking begins, queued ETH starts a new seven-day reward stream.

---

# Last-staker protection

If the final LP staker withdraws while a stream is still running, DamesBounty freezes the stream.

The remaining undistributed ETH is moved back into:

```text
queuedRewards
```

It remains there until LP tokens are staked again.

Therefore time passing while nobody is staking cannot consume reward ETH.

---

# ETH solvency accounting

DamesBounty tracks:

```text
totalRewardsFunded
totalRewardsClaimed
```

Outstanding reward liabilities are defined as:

$$
R_{outstanding}
=
R_{funded}
-
R_{claimed}
$$

The contract checks that:

```text
DamesBounty ETH balance
>=
outstanding rewards
```

This creates a direct relationship between reward accounting and actual ETH held by the contract.

---

# LP solvency

DamesBounty separately tracks:

```text
totalStaked
```

The core LP solvency relationship is:

```text
LP tokens held by DamesBounty
>=
totalStaked
```

The owner has no function allowing staked LP tokens to be rescued from the contract.

---

# Claiming rewards

A staker can claim accrued ETH using:

```solidity
claim()
```

or direct payment to another address using:

```solidity
claimTo(address payable recipient)
```

Reward state is updated before the external ETH transfer.

The claim path also uses a reentrancy guard.

---

# Pausing

DamesBreeches and DamesBounty include emergency pause functionality.

For DamesBounty, pausing prevents:

- new LP stakes
- new reward funding

It deliberately does **not** prevent:

- LP withdrawals
- claiming already-earned ETH

Users therefore retain access to their assets during a pause.

Because reward funding is part of the same transaction as DAMES minting, minting cannot silently continue while DamesBounty is unable to accept ETH.

The entire mint transaction instead reverts.

---

# Immutable protocol relationships

DamesBounty stores the DamesBreeches address immutably.

DamesBreeches allows its DamesBounty address to be configured only once.

Before accepting the address, DamesBreeches verifies that the proposed DamesBounty contract reports:

```text
damesBreeches == address(this)
```

Once configured, the Bounty destination cannot be redirected to another contract.

# Security architecture

The contracts deliberately minimize the number of moving parts.

Important controls include:

### Atomic ETH reward funding

Rewards are funded using `msg.value`.

There is no separate reward amount parameter that could report assets that were never transferred.

### Reentrancy protection

Asset-moving functions use `ReentrancyGuard`.

### Checks-effects-interactions

Reward accounting is updated before ETH is transferred during claims.

### Safe LP transfers

ERC-20 LP movement uses OpenZeppelin `SafeERC20`.

### Hard token cap

DAMES cannot exceed:

```text
21,000,000
```

### Immutable curve

The production curve scale:

```text
100 ETH
```

cannot be changed after DamesBreeches deployment.

### Immutable Bounty after setup

DamesBreeches cannot redirect mint ETH after its Bounty has been configured.

### No Breeches ETH custody

Successful mint ETH leaves DamesBreeches during the same transaction.

### No LP rescue mechanism

DamesBounty provides no owner function capable of extracting users' staked LP.

# Trust and administration

The contracts use narrowly scoped administrative controls for emergency pausing.

`Dames.sol` uses OpenZeppelin `AccessControl`.

`DamesBreeches` holds the token's `MINTER_ROLE`.

The `DEFAULT_ADMIN_ROLE` controls the ability to modify token roles. For the minter set to become permanently immutable, the default admin role must be renounced after deployment configuration is complete.

Users should verify current role ownership directly on-chain rather than relying solely on documentation.

DamesBreeches and DamesBounty ownership primarily provides emergency pause/unpause functionality; it does not provide a treasury withdrawal path for mint ETH or staked LP.

# Economic model

DAMES aligns three groups:

### Minters

Minters acquire newly issued DAMES from a deterministic curve.

### Liquidity providers

Liquidity providers supply DAMES/ETH liquidity and receive Uniswap v2 LP tokens.

### LP stakers

LP holders can stake those tokens in DamesBounty and receive the ETH generated by protocol minting.

The resulting flow is:

```text
Demand for new DAMES
        │
        ▼
ETH enters DamesBreeches
        │
        ├────► DAMES issued to minter
        │
        └────► ETH sent to DamesBounty
                         │
                         ▼
                  LP stakers earn ETH
```

The protocol therefore does not need inflationary staking emissions.

The asset distributed to liquidity providers is the same asset used to acquire newly issued DAMES:

```text
ETH
```

# Design philosophy

DAMES is intentionally small.

The protocol does not attempt to combine:

- NFTs
- governance
- lending
- leverage
- multiple reward tokens
- rebasing
- reflections
- complicated token taxes
- mutable issuance parameters

The core proposition is instead:

> **Mint DAMES with ETH. Provide DAMES/ETH liquidity. Stake the LP. Earn the ETH used to mint DAMES.**
